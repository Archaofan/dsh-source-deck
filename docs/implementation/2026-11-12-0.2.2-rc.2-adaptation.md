# 0.4.2：适配 DSH 0.2.2-rc.2

> 中文（默认）

用户于 2026-11-12 选择方案 B：共用开发沙箱先升级到最新官方 RC `0.2.2-rc.2`，SourceDeck 适配并发布 `0.4.2`，README 与市场条目同步，验收后再讨论生产。生产 Desktop 仍为 `0.2.2-rc.1`（装 0.4.1），本轮未操作。用户当天确认：“工作台的项目现在到底支不支持最新的 rc 版本，readme 有没有明确说明，插件市场是否也更新”——本文件即这三问的落地记录。

## 固定基线

- tag `dsh-v0.2.2-rc.2`，commit `ddac96760b6edf8fa0fe17cbdcf0b512f4c12b2c`；GitHub Release `2026-11-11T11:33:06Z`，npm 发布 `2026-11-12T02:16:12Z`（`dist-tags.next`）。
- Cordis 仍为 `4.1.0`；上游 pnpm `11.28.5`、Node engines `>=24.9.0`（本机 Node 26.7.0）。
- 上游没有 `docs/upgrade-guide/v0.2.2-rc.2/`，接口证据取自源码与类型（见[接口差异](../research/2026-11-12-0.2.2-rc.2-interface-delta.md)）。
- 官方 RC 仍标为预发行；本产品只维护这一个 RC 基线，不承诺 alpha。

## 沙箱升级（先于产品）

旧基线 rc.1 的源码归档为 `sandbox/dsh-desktop/archives/rc-0.2.2-rc.1-20261112T135229Z/`（`git archive` 的源码 tar + home/electron-user-data/appdata/localappdata/tmp/logs/scripts/baseline/status；**不含 3 GB 的 `upstream/node_modules` 与构建产物**，回滚方式为在 upstream checkout `dsh-v0.2.2-rc.1` 后执行 `pnpm install --frozen-lockfile`，本地 pnpm store 已缓存）。`baseline.json` 改为 `0.2.2-rc.2`，`productionVersion` 仍 `0.2.2-rc.1`，`sandboxRelation=ahead-of-production` 并写入用户批准（`upgradeApproval`）。

命令与结果：

```powershell
git -C sandbox/dsh-desktop/upstream fetch --depth 1 origin tag dsh-v0.2.2-rc.2   # exit 0
git -C sandbox/dsh-desktop/upstream checkout --detach FETCH_HEAD               # HEAD ddac9676…，status 干净
pnpm install --frozen-lockfile --config.confirmModulesPurge=false              # exit 0，3m34s
pnpm run build                                                                # 10 passed / 0 failed / 195.86s，371 client artifacts
pnpm --filter @deepseek-ai/dsh-desktop exec install-electron                  # exit 0
pnpm --filter @deepseek-ai/dsh-desktop run prepare:primary-runtime            # exit 0，Office 往返通过
```

第一次安装卡住：`pnpm install` 在 supply-chain 校验后长时间无进度，进程空闲。原因是缺少非交互模式下的确认输入；设置 `CI=true`（不改 frozen-lockfile）后同一命令 3m34s 完成。该处理只用于沙箱上游安装，不用于生产 profile。

**沙箱脚本适配（rc.2 改动）**：`runDesktopCli` 在 0.2.2-rc.2 从两个参数变为一个 `supportDir`，`sandbox/dsh-desktop/scripts/desktop-cli.mjs` 原来传 `(development/project, targets/win-x64/runtime)`，导致插件安装报 `Cannot find module …development\project\primary-runtime\dependencies\pnpm\bin\pnpm.mjs`。改为只传 `targets/win-x64/runtime` 并检查其中的 pnpm 后，安装恢复。未改上游源码。

## 产品改动

- `package.json`：`0.4.1 → 0.4.2`；六个 DSH peer（`dsh`、`typert-protocol`、`session`、`tool-executor-native`、`tools`）与全部官方 Client 类型 devDependencies 精确 `0.2.2-rc.2`；Cordis 保持 `4.1.0`。
- `zod` `4.4.3 → 4.6.6`：`@deepseek-ai/dsh-typert-protocol@0.2.2-rc.2` 精确依赖 `4.6.6`，旧类型缺 `validate`/`validateAsync`，`tsc` 在 `src/remote-info.ts` 报 5 处 `TS2322`。升版后 `tsc` 退出 0。
- `pnpm-workspace.yaml`：`minimumReleaseAgeExclude` 更新到 rc.2 全量条目并加入 `zod@4.6.6`。
- **没有改动任何 `src/` 代码**：rc.2 的契约差异全部是新增可选字段（`insertQuote` 的 `summary`、`consumeOlder`、`conversation.chat.markdown.fence`、`enter.allowEmpty`），SourceDeck 未使用；平台模块表、右栏 slot、native executor 与 rc.1 相同。

## 实际 Host 验收（无模型）

实际 Host 为 `0.2.2-rc.2-ddac967`（页面标题栏与 CDP 读取 `document.title` 均为 `… — DSH 本地构建`）。通过 Electron renderer 的 CDP（`127.0.0.1:19322`）实际操作并回读 DOM：

- 输入区出现「资料台」按钮（`aria-label=资料筛选台`）；打开右栏 tab，旧会话数据正常重放（3 张候选卡、保留/排除状态）。
- 「手动添加资料」输入 `https://example.com/source-deck-adapt` → 「加入候选」生成「补充资料 · 1/1」卡片，对话卡片同步。
- 对补充卡片点「✓ 保留」→ 面板计数 `✓ 2 · ✕ 0 · 待筛选 1`，出现「撤销判定」入口；点「引用到对话（2 条）」→ 输入框出现 `SourceDeck · 2` chip，正文保留、未自动发送。
- 账号菜单 → 设置 → 「资料台」section 加载来源范围策略、快速预设、标记说明、检索指导语与「保存策略」「清除资料台数据」；保存提示「已保存：LLM 自主 · …」。
- 「清除资料台数据」弹出原生 confirm（“清除资料台全部域数据（不影响会话记录）？”），接受后提示「已清除资料台数据。」。
- 控制台只有 Electron 既存的 CSP 开发警告，没有 SourceDeck 的 error；`role="alert"` 为空。

证据：`sandbox/dsh-desktop/test-workspaces/dsh-source-deck/rc2-deck.png`（深色中文，资料台与候选卡）、`cdp-*.mjs` 与 `probe-*.js` 探针、`sandbox/dsh-desktop/logs/desktop.log`。

- Electron 原生 125% 缩放、真实中文 IME/附件组合、屏幕阅读器播报与真人观察未覆盖；四宽四主题与性能矩阵未重跑。
